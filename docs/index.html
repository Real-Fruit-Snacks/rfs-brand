The changelog

§1

Colour

Two themes with the same structure and the same hues. Nightshift is the default; Dayshift is derived from it, with values shifted until every text colour passes WCAG AA (4.5:1) on bg, surface and raised. The accent is Ember.

Every text colour, on every surface

Measured contrast, both themes. AA asks for 4.5:1 for text and 3:1 for control borders. Before 1.2.0, Dayshift Amber measured 4.46:1 on bg, and mute, Ember, Amber and Mint all fell short on raised. Each moved a few steps darker. Nightshift didn't change.

Ember
The brand, once per screen. Glow in Nightshift only. Never for errors.
Mint and Raspberry
Status, not decoration. Mint only ever means OK; Raspberry only ever means failed.
A word with every status
Pair the colour with ok, warn or fail, or a line that says what happened. To red–green colour-blind readers, Dayshift Ember and Amber look the same, and Mint and Raspberry come close.
Focus
A 2px Ember outline with a 3px offset on every focusable element. Press Tab on this page to see it.
Never
Gradients, or a third accent.

§3

Mark: the Caps Tile

RFS in Plex Mono SemiBold, centred on a rounded tile, with an Ember rule beneath. The letters are always white.

Tile
64-unit grid, corner radius 14 (0.219 × side). #1A1D24 in Nightshift, #1A1B1E in Dayshift.
Letters
28 units, tracking −1.5, baseline at 43. Always white.
Rule
36 × 4 units, radius 2, at y = 48. Ember, the theme's value.
Clear space
One corner radius on every side. Smallest size 16 px.

At 16 px

The master's letters blur into a grey bar, so favicons and icons at 48 px or less use the small-size mark: the same tile, colours and rule, with the letters redrawn on the 16 px grid in 4-unit strokes.

Lockup: the tile and the wordmark, gap 0.3 × the tile's side, wordmark cap height about 0.55 × the side.

Don't rotate it, outline the colour version, recolour the letters, put it on Ember (use the single-colour white version), or bake the glow into an asset.

§4

Voice

Four traits, each with a test. First person singular is correct for one maintainer. Sentence case everywhere, including headings.

Plain

Short sentences. Concrete nouns. The reader is busy and competent.

Could a tired admin at 2 am act on it?

Specific

Versions, OS names, command names, numbers.

Is every adjective replaceable with a fact?

Dry

Humour lives in details, like a flag name or a commit message. Never in the headline.

Still funny with the emoji removed? There are no emoji.

Honest

Say what it doesn't do. “Tested on” is a list. Known issues go above the fold.

Is the first limitation visible without scrolling?

Banned blazing powerful modern seamless supercharge awesome Welcome! coming soon and every emoji and exclamation mark.

§7

Repo cover v2

Every tool repo gets one cover: the image under the README one-liner, the docs site's og:image and the GitHub social preview, all from one docs/assets/cover.toml rendered by tools/make-cover.py. Most people see it as a card 400 to 500 px wide, so it's built for that: a big name, one sentence, and one panel that shows what the tool does. Don't draw covers by hand; change the tool and re-run it.

Judged at 400 px

That's this cover at the width of a Slack, Discord or X card, where everything is a third of its size and anything drawn under about 20 px turns into a grey line. make-cover.py --preview shows a cover at 1200, 830 and 400 px in both themes; judge it there, not at 1200. The tool refuses text that won't fit rather than shrinking it.

The parts of a repo cover
PartRule
NamePlex Mono 600, as large as the 480 px column allows, up to 120 px. A name that would be under 80 px breaks after a hyphen onto two lines.
RuleEmber, as wide as the name's widest line, below the descenders. It draws in on load.
DescriptionThe README one-liner and nothing else: Plex Sans 600 at 30 px, one line or two even ones, no trailing period.
Panel528 × 448, one of the four kinds below. Values come from a real run or the README's examples, never invented.
MotionOnce, on load, §8's motions only, 3.5 s at most. An <img> may ignore reduced motion, so nothing flashes, loops or moves larger than a line, and the still frame is the finished cover.
OrgThe RFS tile and REAL-FRUIT-SNACKS in the bottom-left corner.

Four panel kinds

Flow for a tool that turns one thing into another: input, the tool on an Ember connector, output. Terminal for a command: six lines at most, and it types. Art when the tool has a UI and draws itself. Screenshot when the UI is too detailed to draw, cropped to what still reads.

§8

Motion new in 1.2.0

Motion brings the brand's own parts to life; it never decorates. Both themes move the same way, and only Nightshift glows. There are four motions, and this page moves in those four ways and no others.

--rfs-dur-fast 150ms
Hover, press, focus.
--rfs-dur-base 250ms
State changes: toggles, menus, copy confirmations.
--rfs-dur-slow 600ms
Entrances and the theme switch.
--rfs-type-rate 45ms
per characterA terminal typing its command.

Reduced motion is on, so each specimen below is its finished still frame. That's the rule working.

The rule draws in

Left to right, under a name or the wordmark. Once, on load.

port-sync

A terminal types

45 ms a character, then its output a line at a time. The cursor blinks twice, then stays.

$ ./install.sh
ok   carify 1.1.0 installed

The dot grid warms

To Ember around the pointer, in Nightshift, for fine pointers only. Dayshift has no glow.

Move the pointer hereDayshift: no glow, by designOn touch screens the grid stays still

The theme sweeps in

In a circle from the control that switched it, at 600 ms.

An entrance totals 1.2 s at most and never delays reading the headline. Nothing loops except the cursor's two blinks. Every motion sits inside prefers-reduced-motion: no-preference. No parallax, no scroll-jacking. Repo covers are the one exception: a cover may run to 3.5 s, since its terminal types, and because an <img> can ignore reduced motion, it has to be safe without it (§7).

§9

Terminal and code new in 1.2.0

Terminals on covers, sites and docs use one palette, the same one tools/make-cover.py draws. In cover.toml a line's prefix picks its colour; the prefix isn't drawn, so the words must say what happened.

Starting a repo

The README order is fixed: one-liner, install, context, what's in it, tested on, known issues, configuration, license.

  1. Copy templates/repo/README.md, fill it in and delete the HTML comments.
  2. Work through the settings checklist: description, topics, social preview, branch, releases.
  3. Copy templates/repo/cover.toml to the repo's docs/assets/, fill it in and run make-cover.py. Commit the cover-* files and upload social-dark.png as the social preview.
